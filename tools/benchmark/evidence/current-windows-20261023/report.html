What these results mean

These are verified complete-operation rates on one shared Windows host. Each rate is the median of five rotated windows; latency pools successful requests across those windows. Sorting the medians gives a descriptive ordering, not a universal or statistically certain winner. Every failed and invalid cell remains in the data.

Native UDP, matched Python UDP/OSCORE, common Go DTLS and HTTP/3 use different clients. Select a comparison within one stratum. Do not subtract their times to estimate cryptographic cost. Python/GIL scheduling, authentication and full-body verification can limit the protected comparison before the server saturates.

Coaptic configurations share one library and the same capacities. Bare UDP and reusable-buffer UDP spin; Mio waits using direct readiness; async uses the native wait/progress API on a current-thread Tokio runtime. Reusable means a caller-owned receive scratch buffer, not a second protocol library. The codec endpoint is a narrower reference and receives no full-stack rank. DTLS wrappers for Coaptic/coap-rs are test integrations, not a core Coaptic DTLS feature. HTTP/3 is a separate protocol reference.

Where CPU time is going

Host boundary: strongest broad lead. The last eligible Linux matched-core run charged 59–90% of candidate server process CPU to system time across its four 64/1024-byte security cells. Inclusive samples repeatedly reached syscall/scheduler code. That is historical Linux process accounting, not current Windows function attribution or blocked time. It makes a 2× whole-server gain from small parser/copy changes alone unlikely in that cohort.

Core: dispatch and authenticated encryption remain. Socket-free physical callchains contained 337 unprotected and 792 protected App-rooted samples. They point to dispatch/poll and server AES/CCM open/seal work. CPU-mode, throttling and inline completeness limit formal attribution. Client crypto was separated by ancestry; flat AES samples cannot all be charged to the server.

Confirmed memory work. Windows emitted code proved redundant response copies and unconditional Inner/catalog scratch initialization; those were removed. Direct AAD encoding removed its intermediate and copy. Remaining response option construction still initializes 24 descriptors and copies 576 bytes in the inspected emission. Each OSCORE open/seal constructs a local schedule; the inspected x86-64 object wipes 704 bytes on drop, twice per ordinary exchange. These are emitted-work facts, not measured percentages of CPU.

Next ideas, ranked for a focused experiment

  1. Receive into reserved pool slots; batch only what is already ready. A cloud transport could use a bounded engine RX grant and OS truncation reporting, then process a small admitted burst. Linux recvmmsg/sendmmsg can amortize system calls. Keep existing pool limits, timer/fairness bounds and partial-send ownership; never wait to fill a batch. This mainly targets concurrent traffic, not C1. It is a proposal, not a result.
  2. Register a timeout only if an operation actually suspends. The async path currently polls deadline timers before socket work. A reviewed fast path could preserve deadline precedence using a fresh clock, try immediately, and register the timer on Pending. Recheck expiry and cancellation carefully. Previous staging removed empty App polls without a consistent CPU gain; removing a logical poll is not enough.
  3. Explicit prepared crypto profile. RustCrypto CCM borrows its cipher, allowing preparation once per context instead of each packet. A sender-only retained schedule adds approximately 704 bytes of payload per context on the inspected x86-64 layout, plus row/alignment/initialization effects. Count every configured row, including empty/revoked rows, and keep schedules secret until drop. A bounded batch-scoped schedule is another idea if traffic can share it. Keep raw-context and SmallDevice defaults unchanged. A prepared profile needs its own declared context bound and must fit its whole-App/memory budgets; the 704-byte cipher alone exceeds the default 512-byte raw-context ceiling. Neither variant is implemented or timed.
  4. Encode sorted response option groups without constructing a full descriptor array. Preserve all 24 options, stable order for repeated Location values and OSCORE classification. This targets a demonstrated 576-byte construction copy, but crosses encoder interfaces and may buy little whole-server CPU. Measure an isolated App batch before broad plumbing.

Both 50% CPU-reduction targets remain open. This refresh ranks complete network operations; it does not qualify the separate paced-load CPU target. The new isolated server-App CPU probe is still unmerged and lacks native qualification. No prepared-key, syscall-batching or new profiling infrastructure was introduced for these rankings.

Method, resources and reproducibility

Five windows per stratum, seed 20261023; at least 60 seconds between same-stratum windows. Responses 64/1024/65536 bytes; concurrency 1/4/16; CON/NON or HTTP/3 warm/cold. Operations per cell 256/128/16, one warmup per worker, one-second complete-operation deadline. Status, Token/MID, Content-Format, ETag/ranges and every response byte are verified. Real sockets and external processes prevent optimization of exchanges away; Criterion is not needed to make socket I/O observable.

Coaptic Default allocated profile: one route, blockwise on, RX/TX four 1472-byte slots each, dedup eight, Observe four, RX body one and TX bodies two; body capacities round the response to 1024 bytes. Startup pools are reused. All adapter variants keep the same core capacities. Per-row RSS is the largest retained current process-tree snapshot, not peak RAM; CPU spans driver startup, warmup and exit as well as operations, with coarse Windows accounting. Neither is a whole-system memory requirement or clean CPU/op ranking.
