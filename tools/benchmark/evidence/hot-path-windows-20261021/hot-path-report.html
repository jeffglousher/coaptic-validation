What changed

  • Reuse Observe planning already computed for the request.
  • Skip registration routing for ordinary requests; retain terminal Q-Observe selections.
  • Prepare deferred snapshots only when a deferred dispatcher can use them.

Authentication, replay protection, exact payload checks, deduplication, admission, deadlines and timer progress remain in place. All pools and protocol capabilities stay the same.

Where the time goes

The instrumented64B server averages8.95µs per active poll: receive 0.85µs, send 6.35µs, residual 1.76µs. Instrumentation and nested clocks perturb these values. No hot allocations or whole-body snapshots/comparisons were recorded in these GET probes.

Protected timings also include the client. With the same server configuration, native complete exchanges are about 14µs; Python+independent OSCORE verification is about 140µs. This demonstrates driver/runtime sensitivity, not an isolated cryptographic slowdown.

Further costs found, retained for focused follow-up
  • OSCORE reconstructs and re-encodes inner messages through repeated scratch buffers.
  • Native load driver allocates request/ETag vectors, initializes65,535B per operation, and changes a socket timeout per receive.
  • Busy polling repeatedly checks the socket and timers. Receive staging also detects oversized datagrams and cannot simply be removed.

No expanded-key cache or extra buffers were added. These candidates need their own attribution and invariant checks before changes.
